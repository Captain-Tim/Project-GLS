Software Testing Fundamentals

From Zero to Test-first · 從零開始建立測試思維 · 2026.11.27

01. Motivation ｜動機

適合尚未建立自動化測試習慣的開發者。目標是能開始設計、審查與維護測試，尤其是在 AI 輔助開發中，而非完整介紹軟體測試研究領域。

AI 降低了撰寫程式碼的成本，但程式碼是否符合需求仍然需要驗證。自動化測試將一次性的人工檢查轉為可以反覆執行的驗證資產。修改、新增功能或重構時，可以重新檢查既有行為。

測試的價值不只在於找 Bug。它迫使我們釐清規格、設計清楚的介面、隔離外部依賴，並降低 Debug 與重構的成本。開發者通常負責自身模組的測試，QA、SDET 或 Verification Engineer 則可能負責更廣泛的驗證策略與工具，實際分工因團隊而異。

02. Fundamentals ｜測試的本質

測試是在給定條件下，檢查實際行為是否符合預期行為。

int Max(int a, int b) {
    return a > b ? a : b;
}

// Test Code
assert(Max(3, 5) == 5);
assert(Max(5, 3) == 5);
assert(Max(3, 3) == 3);

Test Case 包含輸入、必要的初始狀態及判定條件。Test Suite 是測試案例的集合。所有測試通過，只代表已驗證的情境沒有發現違反預期的行為，不代表所有可能輸入都正確。

Test Oracle（測試判定依據）

Expected Output 可以手動指定，也可以由獨立參考模型（Reference Model）產生，例如用 Direct DFT 驗證 FFT，並考慮浮點誤差。不要直接複製 Production Code 的運算邏輯作為答案，否則兩者可能共享相同錯誤。

也可以驗證必要的數學性質，不必知道每筆輸入的精確答案。這是 Property-based Testing 的基本思路。

03. Test Design ｜如何選擇測資

十筆同類型測資不一定比五筆不同情境更有效。先理解規格，再選擇能辨識不同錯誤的測資。

以 Clamp 為例

Clamp(x, lower, upper) 將 x 限制在合法區間內，假設 lower ≤ upper。固定區間 [0, 10]。

方法測資 x目的
Equivalence Partitioning（等價類別劃分）-1, 5, 11下界外、區間內、上界外三種行為
Boundary Value Analysis（邊界值分析）-1, 0, 1, 9, 10, 11驗證邊界與相鄰整數
Extreme / Corner CasesINT_MIN, INT_MAX型別極限。另可改變上下界，測試單點區間

例如只選擇區間內的正數、負數與零，錯誤的 return x; 也可能全部通過。先涵蓋規格中的基本行為，再考慮特殊數值與組合。

Property-based Testing（性質測試）

Clamp 的輸出必須落在區間內，但僅驗證這項性質，錯誤的 return lower; 也會通過。排序則可驗證兩項性質：輸出單調不遞減，以及每個元素與其出現次數保持不變。對一般整數升冪排序，兩者共同充分描述結果，不涉及穩定排序等額外規格。

充分的數學條件與充分的測試不是同一件事。即使性質能唯一決定正確答案，有限的測資仍無法證明性質對所有輸入成立。

Black-box 與 White-box

Black-box Testing 根據規格設計案例。White-box Testing 利用內部結構、分支與路徑找出盲區。兩者互補。利用 Implementation 尋找測試情境，利用 Specification 判定測試結果。若規格不變，避免把不必要的內部步驟固定成驗收條件。

04. Testing Levels ｜測試的範圍

層級驗證目的封包系統範例
Unit個別可獨立驗證的單元Round Robin 是否正確選擇 Queue
Integration多個模組協同運作Queue 狀態是否正確傳給 Scheduler
System完整系統符合系統規格吞吐量、延遲、封包遺失
End-to-End（E2E）完整使用流程從封包輸入到最終傳輸結果

Unit 全部正確不保證整合正確，例如一個模組以 Byte 為單位，另一個以 Bit 為單位。反過來，E2E 通過也不保證各模組正確：規格要求先乘 2 再除 2，錯誤地先乘 4 再除 4 也可能得到相同最終結果。Unit Test 有助於縮小錯誤範圍。

Test Pyramid 建議大量快速的 Unit Tests、適量 Integration Tests、較少昂貴的 E2E Tests。這只是資源配置的常見起點，並非固定比例。System 與 E2E 的範圍也可能重疊。

Regression Testing（回歸測試）

修改後重新驗證既有功能是否遭到破壞。這是依測試目的分類，不是另一個測試層級。既有 Unit、Integration、E2E Tests 都可以成為 Regression Tests。

05. Test Quality ｜如何建立可信的測試

Coverage 與 Mutation Testing

Line Coverage 衡量可執行程式碼行的覆蓋程度，Branch Coverage 衡量分支結果，Condition Coverage 衡量基本布林條件的真假結果，Path Coverage 關注執行路徑。100% Line Coverage 不代表所有條件或測資都已驗證。Coverage 適合用來找盲區，不是品質保證。

Mutation Testing 刻意產生程式變異，再執行既有測試，觀察能否偵測變異。若 Max(a,b) 的比較從 > 改為 ≥，兩個值相等時雖然選擇不同變數，回傳數值卻相同。這是 Equivalent Mutant，不應被當成測試不足。判斷等價性本身可能很困難，因此 Mutation Score 亦有限制。

獨立、可重現的測試

測試不應依賴其他測試先執行。否則失敗位置可能不是 Bug 的真正案發現場，錯誤也可能沿共用狀態傳播。單一案例內的多步驟狀態轉移則完全合理。

TEST(AccountTest, WithdrawReducesBalance) {
    Account account(100);                // Arrange
    account.Withdraw(30);                 // Act
    EXPECT_EQ(account.GetBalance(), 70);   // Assert
}

Arrange–Act–Assert（AAA）分別建立初始條件、執行行為與驗證結果。上述為 GoogleTest 示意，假設 Account 提供相應介面。

Flaky Test 是在沒有相關程式變更時仍出現不穩定結果的測試。常見原因包含共用狀態、時間、外部依賴、並行及隨機性。固定 Seed 適合可重現的測試，變動 Seed 可探索新輸入，但須保留失敗測資、Seed 及必要環境資訊。真正的反例應重現、修復並納入 Regression Suite。隨機找到真 Bug 不等於測試本身不可靠。

測試成本與停止條件

測試越多不一定越有價值。每新增一筆案例，問自己：這筆測試有機會發現哪一種既有測試無法發現的錯誤？若無法說明，可能已進入邊際效益遞減的區域。這是思考工具，不是可證明充分性的判準。

06. Testability ｜測試如何影響架構

容易測試的設計通常具有清楚的依賴、可控制的輸入、可觀測的輸出及可重現的行為。

// 難以控制外部市場資料
bool ShouldBuy() {
    return GetLiveMarketPrice() > GetLiveEMA();
}

// 核心邏輯與資料取得分離
bool ShouldBuy(double price, double ema) {
    return price > ema;
}

後者可以直接驗證大於、小於、等於三種情境。這種設計讓我們自然思考低耦合、職責分離及介面設計，但不要為了測試過度拆分函式。

Test Double（測試替身）

若下單功能必須呼叫券商 API，可以利用 Dependency Injection 從外部提供 Broker 依賴，測試時替換成可控制的 Test Broker。

種類用途
Stub提供指定回應，例如回傳拒絕或拋出逾時例外
Mock驗證必要的互動，例如風險檢查失敗時不得下單
Fake簡化但可運作的替代實作，例如記憶體中的訂單紀錄

替身提高可控制性，卻可能與真實依賴產生落差。只模擬測試需要的行為，不要為了測試重建完整券商系統。真實介面的相容性仍須透過整合驗證確認，必要時使用安全的 Sandbox。

測試應保護行為而不是綁定不必要的實作細節。若 Quick Sort 改為 Merge Sort，排序結果的測試應保留，但 Pivot 選擇的測試可能失去意義。White-box 選出的測資只要仍驗證規格，就不必因重構而捨棄。

07. Test-first ｜入門開發方法

方法核心思想Trade-off
Test-last先實作，再寫測試容易開始，但測試可能被實作帶著走
Test-first先定義測試，再實作驗收標準較獨立，需要先理解規格
TDD小步反覆 Red → Green → Refactor快速回饋，要求更細的迭代紀律
BDD以可理解的行為情境促進協作與開發有利需求溝通，完整流程可能增加摩擦
ATDD共同定義驗收測試，再開發對齊需求，需事先釐清驗收標準

這些方法可以搭配使用，不是成熟度階級。入門先採用輕量 Test-first，保留驗收標準先於實作的價值，不必立即嚴格採用 TDD。

什麼時候可以開始實作？

先對照明確規格，建立有代表性的 Black-box Tests。以 Round Robin Scheduler 為例，假設從 index 0 起始，成功選擇後從下一個 Queue 開始搜尋，全部為空回傳 -1 且不改變輪詢位置，Reset 恢復起始狀態。這些是假設的範例規格，實際專案應明確約定。

規格測試名稱範例
依序輪詢與循環RotatesAndWraps三個 Queue 持續非空 → 0, 1, 2, 0
跳過空 QueueSkipsEmptyQueues[false,true,false] → 1
全部為空EmptyDoesNotAdvance先選 0，再全部為空 → -1，再全部非空 → 1
單一 QueueSingleQueue[true] → 0, 0；[false] → -1
ResetResetsToInitialState選 0 後 Reset，再選 → 0

表中每一列從獨立初始狀態開始。規格與測試的對應關係（Requirements Traceability）有助於發現遺漏，但不保證測試充分。實作後再使用 White-box 與 Coverage 補足盲區。之後遇到真實 Bug，再增加 Regression Test。

不要把「所有高風險情境都已考慮」這類難以客觀判定的敘述變成形式化打勾流程。測試充分性需要工程判斷，透過實際經驗逐漸改善。

修復 Bug 時先重現

新增能重現 Bug 的測試，確認它因正確原因 FAIL，再修復 Production Code 並確認 PASS。這比只觀察修復後 PASS 更有說服力，因為也驗證了測試確實能辨識原本的錯誤。

08. AI-assisted Development ｜驗證機制

Testing Framework（如 C++ GoogleTest、Python pytest）提供測試命名、自動發現、獨立執行、失敗報告、過濾、Fixture 與參數化測試。比起原生 assert，框架更適合大型測試集合。原生 assert 在 NDEBUG 定義時可能被移除。

CI（Continuous Integration）可以在程式變更時自動執行驗證，搭配受保護分支與必要狀態檢查，才構成強制 Quality Gate。

驗證方式用途
Build / Compiler Warnings能否編譯及可疑寫法
Static Analysis不執行程式，分析潛在缺陷
Dynamic Analysis執行時檢查記憶體與 Undefined Behavior 等問題
Functional Testing行為是否符合規格
Code Review設計、架構及可維護性

合法且安全執行的程式仍可能做錯事，例如 Add 回傳 a - b。不同工具互補，不要把單一檢查當成正確性保證。

Test Governance（測試治理）

AI 可以新增測試、補足案例及重構測試程式碼，但修改 Expected Output、放寬 Assertion、刪除或停用既有測試時，應由人類確認原因與規格。不能只因為 Production Code 無法通過測試就修改答案。若測試本身有錯或規格正式改變，則應允許有依據的修正。

Risk-based Testing（風險導向測試）

評估錯誤嚴重程度、可能性、偵測難度及影響範圍。視覺調整通常容易發現且後果較小，風險控制演算法則需要更嚴格驗證。共用函式即使只修改三行，也可能影響大量功能。

建議先建立固定的最低品質門檻，例如 Build 和既有 Regression Tests，適合的分析工具再納入。由人類判斷是否提高驗證強度，AI 提供建議與執行，不自行降低驗收門檻。暫不建立複雜評分公式。

09. Getting Started ｜第一個實際專案

從一個規格清楚、可獨立執行的小模組開始，例如 Scheduler 或 DSP 運算。以下是建議起點，而不是強制流程。

  1. 定義可觀察的功能行為，釐清模糊的規格與介面。
  2. 請 AI 根據規格撰寫一小組具明確目的的測試。審查重要 Expected Output。
  3. 在可執行的初始版本中確認新功能尚未通過相應測試，再請 AI 實作。
  4. 執行新舊測試，必要時依實作與 Coverage 補足盲區。
  5. 把可重複執行的測試保留在專案中，建立 CI 或本地固定驗證命令。
  6. 遇到 Bug 時先重現再修復，逐步累積 Regression Suite。

實際使用後觀察哪些錯誤逃過測試、哪些測試重複、哪些架構難以驗證、哪些驗證成本過高，再調整策略。

先使用，再改善。測試的目標不是最大化案例數量，而是在合理成本下建立值得信賴且能持續演進的驗證機制。

學習狀態：核心觀念已透過對話問答驗證，完整 Test Suite 的實作、框架操作與 CI 設定仍待實際練習。
